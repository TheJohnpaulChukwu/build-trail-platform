# 03 — Database schema and authorization

The [detailed data/API specification](../../IMPLEMENTATION_DATA_AND_API.md) refines this logical model with immutable course metadata, durable enrollment epochs, preference locking, explicit milestone-state writes and complete multipart transfers. Implement those refinements together with the constraints below.

## Identity conventions

Use UUIDs for stable courses, versions, lessons, milestones, sections and items. User IDs reference `auth.users.id`. Slugs are presentation identifiers, never progress keys. Times are UTC `timestamptz` generated by the database. Revisions are non-negative `bigint`, encoded as decimal strings at JSON boundaries to avoid JavaScript integer precision errors. JSON schemas reject unknown identity fields.

Tables below are the logical migration contract. Foreign keys and indexes must be implemented explicitly; a JSON field is not a substitute for required relational integrity.

## Content tables

| Table | Keys and required fields | Invariants |
| --- | --- | --- |
| `courses` | `id`, canonical `slug`, `visibility`, nullable `active_version_id`, timestamps | Unique slug; active version belongs to this course and has published state |
| `course_routes` | `slug` PK, `course_id`, `is_canonical` | One canonical/alias namespace; direct stable-ID targets; canonical row agrees with courses.slug |
| `course_versions` | `id`, `course_id`, `version_label`, `state`, `schema_version`, `source_hash`, immutable title/summary/language/prerequisites metadata, `published_at`, `created_at` | Unique `(course_id,id)` and `(course_id,version_label)`; retained published snapshots immutable |
| `lesson_identities` | PK `(course_id,lesson_id)` | Stable identity survives removal from an active version |
| `item_identities` | PK `(course_id,lesson_id,item_id)`, `kind` | Kinds: section, checklist, reflection; never change kind/reuse ID |
| `milestone_versions` | PK `(version_id,milestone_id)`, `course_id`, `title`, `position` | Unique position within version; FK to version/course |
| `lesson_versions` | PK `(version_id,lesson_id)`, `course_id`, milestone, slug, title, position, `required`, `body_markdown`, `content_hash`, section mapping | Composite FKs bind course/version/lesson; unique slug and position within version |
| `item_versions` | PK `(version_id,lesson_id,item_id)`, kind, label, position, anchor | FK to stable item and lesson version; stable anchor mapping |
| `lesson_routes` | PK `(course_id,slug)`, `lesson_id` | Routes resolve against pinned version; a removed lesson offers archived notes/current outline |
| `reference_versions` | PK `(version_id,reference_id)`, course, slug, title, Markdown, anchors | Version-owned setup/reference pages |
| `asset_versions` | PK `(version_id,asset_id)`, course, storage path, media type, bytes, SHA-256, purpose | Path immutable; server validates actual content and hash |
| `search_documents` | PK `(version_id,document_id)`, course, lesson/reference ID, section ID, title, plain text | Derived from the same accepted AST; contains no learner data |

Publication uses a constraint trigger/transaction check for active-version state; a foreign key alone cannot check a referenced row's publication state. Add composite foreign keys wherever a course ID is duplicated. Do not permit a progress row to point at a lesson in a different course.

## Learner and operational tables

| Table | Key and fields | Policy |
| --- | --- | --- |
| `profiles` | user PK, display name, `account_state`, created time | Self read; limited RPC for name; state server-controlled |
| `user_preferences` | user PK, theme, reading size, reading font, focus, revision | Self only; validated enums; defaults for absent rows |
| `enrollments` | PK user/course, last lesson/section, activity time, `workspace_revision`, durable study epoch, expanded milestone IDs | Self only; revision increments on any study-record mutation in that course |
| `lesson_progress` | PK user/course/lesson, status, completed time/version, needs_review, revision | Explicit completion; completion version FK to that lesson's snapshot |
| `lesson_notes` | PK user/course/lesson, body, revision, updated time | At most 50,000 Unicode code points and 200,000 UTF-8 bytes |
| `reflection_answers` | PK user/course/lesson/item, body, revision, updated time | Item kind must be reflection; same text limits |
| `checklist_answers` | PK user/course/lesson/item, checked, revision | Item kind must be checklist; one-item writes |
| `lesson_evidence` | PK user/course/lesson, body, revision | Optional plain text self-reported evidence; same bounded text rules |
| `platform_owner` | singleton row, user FK | No browser CRUD; trusted bootstrap/reassignment only |
| `mutation_receipts` | PK user/mutation UUID, operation, request hash, response metadata, expires time | Private schema; successful retry result without reapplying mutation; never stores raw note text |
| `publish_operations` | UUID, owner, course/version, state, archive path/hash, validation report, lease token/expiry, timestamps | Owner read; server/RPC state transitions only |
| `data_operations` | UUID, user, kind, input hash, preview revisions, status, result metadata, expiry | Import/export lifecycle, private object references |
| `deletion_jobs` | UUID, target user UUID, state, session evidence, retry stage, timestamps | Private schema; no FK cascade to auth user because job must survive deletion |
| `user_quotas` | user PK, aggregate text bytes, study record count, enrollment count | Private schema; transactional accounting and per-user lock |
| `security_counters` | action/user/window key, count, expiry | Private schema; atomic throttling |

Ordinary learner rows cascade when their auth user is removed. Course/lesson identities do not cascade when content is withdrawn. `deletion_jobs` stores only minimum operational identifiers and expires after completion retention. The singleton owner FK prevents accidental deletion until ownership is reassigned.

## Mutation boundary

Expose safe SELECT access with RLS. Revoke direct browser INSERT/UPDATE/DELETE on learner/content tables. Grant authenticated callers only narrowly named RPCs, defined in [API contracts](04_API_AND_SYNC.md). This makes revisions, ownership checks, quotas and idempotency impossible to skip with a direct REST update. Also deny caller-assigned revision, timestamp, role and account state.

Use `SECURITY INVOKER` for read-only functions where normal table policies suffice. Mutation RPCs that need revoked table writes use tightly scoped `SECURITY DEFINER` functions: fixed empty search path, fully qualified objects, no dynamic SQL, explicit `auth.uid()`/active-account checks, least-privileged function owner where supported. Revoke default EXECUTE from PUBLIC/anon and grant specific functions only to authenticated or server roles. RLS does not automatically protect privileged function bodies: checks inside them are mandatory.

Service-role-only publishing/import helpers accept a validated actor UUID from the authenticated server handler; the database rechecks current owner/account state. No arbitrary actor argument in browser-callable learner RPCs. Never use a caller-provided user ID as proof of ownership.

## SELECT policy matrix

| Resource | Visitor | Learner | Owner |
| --- | --- | --- | --- |
| Listed active catalogue | Read | Read | Read |
| Retained published version of listed course | Read by explicit version | Read | Read |
| Withdrawn course content | Deny | Deny; private notes remain exportable | Read |
| Draft metadata/Markdown/assets | Deny | Deny | Read |
| Learner rows | Deny | Own active-account rows | Own rows only |
| Upload operations | Deny | Deny | Own owner operations |
| Owner role/private operational tables | Deny | Deny | Access only through required trusted operations |

Enable RLS on every exposed table; inspect grants as well as policies. Protect views with invoker semantics or avoid exposing views that bypass policies. Policy helpers must not recurse through the same policy. `is_active_user()` checks the authenticated UID against an existing active profile; absent/deleting users are denied. Profile and user-quota row creation occurs through an auth-user trigger or trusted setup, not a public profile upsert. Quota rows cascade with the auth user and are initialized before any study write. This prevents stale tokens from recreating data after account deletion.

## Constraints and indexes

Index `(user_id,course_id)` on private data and `(course_id,version_id)` or version-first read keys on content. Add unique version ordering, alias uniqueness and idempotency keys. Index policy predicates; avoid per-row heavyweight joins in normal reads. Require matching item kinds with composite constraints or transaction checks. Reject non-finite numeric simulation parameters in content schema.

Every study write first takes the active-profile shared lock, then the user quota row, corresponding enrollment row, and affected records in deterministic order. Preference writes and imports share this account lock protocol; deletion obtains the exclusive profile barrier. Follow the root data contract for the complete lock graph. It compares record revision, changes one record and increments workspace revision in the same transaction. Imports acquire the same user quota lock and enrollment locks before checking preview revisions. This closes the race between an import preview and a later note save. Concurrent creation uses an upsert followed by row locking; do not lock a nonexistent row and assume it serializes inserts.

## Migration strategy

Ordered SQL migrations are authoritative. Generate TypeScript database types after migrations and fail CI on uncommitted drift. Separate schema changes from content seeds. Seed commands never reset learner rows. Prefer expand/migrate/contract changes; old and new app releases must work during rollout. Check upgrades from the previous schema, not only empty-database installation. Destructive migrations require a concrete backup/restore and rollback analysis during implementation.

The table layout and lock protocol are BuildTrail design choices.
